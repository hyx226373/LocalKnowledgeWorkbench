# 10 日常工作流：工作资料、原位编辑、冷启动分级加载（第 9 轮 B/C/D）

目标场景：选一项工作 → 一键恢复多个文档 → 在同一应用内阅读、编辑、整理。

## B. 工作资料（集合）

**现状核对（第 8 轮之前）**：工作区本来就是全局的、可跨根（标签里可以放任意根的文件），但只有“打开的标签”这一种归属——关掉标签，文件就不再属于这项工作；也没有“同一文件被哪些工作引用”的概念。缺的是一个与标签分离的“资料清单”。

**本轮补齐**：

| 能力 | 做法 |
| --- | --- |
| 把任意根中的文件加入一项工作 | 目录树文件行 ⊕（`data-testid="ref-toggle"`）；侧栏顶部“本工作的资料”列表（`.kb-collection`，主题组件 `collection-row`） |
| 同一原文件被多个工作引用 | 引用只存资源 ID（稳定 ID，外部重命名/移动后仍跟随）；`workspacesReferencing(rid)` 查哪些工作引用了它 |
| 添加/移除不移动、不复制原文件 | 引用是纯元数据，不写 op_log、不触碰文件；移除时确认框写明原文件位置并提示其他引用者 |
| 移除时的标签（第 9 轮产品决定） | 从工作区移除一份资料时，**同时关闭它已打开的标签**（确认框里写明会关闭几个标签）；如果其中有未保存内容，再确认一次（“先不移除 / 移除并关闭”）。关闭后，未保存内容保留为草稿，不写入文件 |
| 一键恢复多个文档 | “全部打开”：按资料顺序在标签中打开，已打开的不重复 |
| 原文件不在原处 | 行显示删除线 + `aria-disabled`，引用保留（文件恢复后可再用），**不自动清理**（第 9 轮产品决定）。行上有“修复…”（`ws-ref-repair`），点击后打开数据迁移窗口的“修复路径”页，可以重新定位文件或重新映射根。这一轮保持这种做法；改成工作台内联修复已登记为后续任务（docs/03 T23）。30 天清理也不会删除只被资料引用的缺失资源 |
| 导出/导入 | `.kblayout.json` 增加可选 `refs`（资源 ID 列表），与标签一样按“根名 + 相对路径”重新匹配；旧文件无此字段照常导入 |

**存储**：`layout` 键值表中的 `workspace.refs:<工作区 ID>` = `[{id, at}]`。不改数据库结构（迁移组负责 schema），也不改 dockview 布局序列化格式；删除工作区时一并删除该键。以后若迁移组提供 `workspace_refs` 表，适配只在 `WorkbenchService.refRecords/addWorkspaceRefs/removeWorkspaceRef` 三处（见 docs/09-接口请求.md）。

**接口**（主进程服务 → IPC → `window.kb`）：`listWorkspaceRefs(wsId)`、`addWorkspaceRefs(wsId, rids[])`（幂等，只接受文件）、`removeWorkspaceRef(wsId, rid)`、`workspacesReferencing(rid)`；`WorkspaceSummary.refCount`，`rootIds` 也计入资料所在的根。

### 全局自建目录（第 11 轮 C）

自建目录是**全局**归类，不是磁盘文件夹，也不属于某一个工作区。

| 键 | 内容 |
| --- | --- |
| `library.vfolders` | `{ v:1, folders:[{ folderId, parentId, name, sort, createdAt }] }` |
| `library.vfolderRefs` | `{ v:1, byFolder:{ [folderId]: resourceId[] } }`。空字符串键是虚拟根上的未归类条目 |
| `library.vfolderClassifyUndo` | 最近一次「按类型整理」的撤销快照 |
| `library.webStubs` | 网页资源尚未接入时的占位（不进 `.kblayout.json`） |

- 一个资源可以同时出现在多个自建目录。添加归属、删除目录、按类型整理都**不移动、不复制、不删除原文件**，也不写 op_log。
- 删除自建目录：子目录的父级改成被删目录的父级；成员并入上一级（没有上一级就进虚拟根）。不关闭面板，不改工作区资料引用。
- 删除工作区只删该工作区的 `workspace.refs:<id>` 和布局，**不清**全局自建目录。
- 导出的 `.kblayout.json` 不含自建目录树。加入工作区也不复制这棵树。
- 侧栏双目录视图的开关、左右目标和分隔比例在 `ui.dirView`（`{ dual, left, right, split, axis }`，以及每栏的 expanded / scrollTop / selected）。单栏时侧栏外观与原来一致，仍用全局 `ui.expanded`。
- 没有阅读器的格式仍列在目录里；打开时提示「暂无阅读器」。
- 按类型整理的默认目录：md/markdown→笔记，txt/log→文本，pdf→PDF，图片扩展名→图片，csv/tsv→表格，json/xml/yaml/yml/toml/ini→数据，代码扩展名→代码，html/htm/css→网页，目录→文件夹，网页资源→网络资料，其余→其他。只**增加**归属。撤销会恢复这些资源原先的归属，并删掉这次新建且已经变空的目录。
- 右键「从该目录移除」只取消这一条自建目录归属，不关面板。「从本工作区移除」沿用原来的移除资料（关本工作区面板、处理未保存）。拖到落点只高亮，真正移动交给拖拽组。

**测试**：`tests/collections.test.ts`（4）；`e2e/e2e-collections.mjs`（14；第 9 轮新增：移除资料时关闭标签、有未保存内容时先确认、失效引用的“修复…”。新截图 `verify/collections-remove-dirty-confirm.png`、`verify/collections-missing-repair.png`）：三个根目录（甲-笔记 / 乙-论文 / 丙-图片）、md/txt/pdf/jpg 四种格式经界面加入同一工作；“第二项工作”引用同一个 讲义.pdf；移除引用后 sha256/大小不变、三个根的文件清单+哈希+mtime 全程不变；重启保持；外部删除后显示不可用。截图 `verify/collections-refs.png`。

## C. 文本与 Markdown 原位编辑

**现状核对**：第 8 轮之前主进程已有 `writeText`（写入前内容进内容寻址备份库 `blobs/` + op_log，可 `undo`），但没有暴露给界面、没有冲突检测；阅读器只读，且文件变化时宿主直接重建视图（会冲掉未保存的编辑）。

**本轮补齐**：

| 要求 | 做法 |
| --- | --- |
| 面板里直接编辑 .txt / .md | 文本视图：阅读 / 编辑；Markdown：预览 / 编辑 / 分栏（分栏时预览实时跟随未保存内容）。模式存进**面板状态**（`state.data.mode`），不改布局格式 |
| 保存走主进程服务层 | 渲染进程 → `api.workspace.textEdit`（仅内置插件可用）→ IPC `textSave` 等 → `TextEditService`（src/main/service/textEdit.ts）→ `FileOpsBackend`（src/main/backend/fileOps.ts）。渲染进程没有任何写盘路径 |
| 保存前看改动 | **第 9 轮产品决定**：用户自己按 Ctrl+S 或点“保存”时**直接保存**，默认不弹差异预览。保存后可以用“撤销上次保存”撤销。工具栏“查看改动”随时可以看差异；“保存前预览”开关（`editor-preview-toggle`）可以按需打开（行级 diff，`src/shared/textDiff.ts`）。**agent 提出的修改计划必须先显示差异预览**：服务层 `UiOps.review(planId)` 返回逐行 diff，如果 agent 的计划没有经过 review 就提交批准，会被拒绝（`ApprovalError 'not-reviewed'`）。目前界面上还没有 agent 入口，这条规则只在服务层强制 |
| 每次保存写恢复记录 | 写入前内容进备份库 + op_log（`detail.via='text-edit'`）；“撤销上次保存”逐级回到上一版；文件在那次保存后又被改过时先确认，当前内容先存进备份库。**不支持“撤销一次撤销”**；撤销冲突时备份下来的内容在“操作记录”（视图 → 操作记录）里那条撤销记录上显示为“恢复撤销前的内容”（2026-10-04 产品决定，`WorkbenchService.restoreUndoBackup`）。恢复本身也记一条写入（`via: 'restore-backup'`），可以再撤销。没有冲突的撤销不提供这个按钮（撤销前的内容就是那次保存的内容，重新保存即可） |
| 外部同时修改 → 冲突 | 打开时记内容 sha256；保存时磁盘哈希不同 → 对话框：**保留我的**（外部版本先备份，可撤销找回）/ **采用外部的** / **对比后再决定**（外部→我的 diff）/ 继续编辑。服务层写入前再校验一次 `expectedHash`，绝不静默覆盖 |
| 其他面板及时刷新 | `api.workspace.onDidChangeFile(rid)`：主进程 fs-change → 按资源 ID 比对内容哈希 → 通知。无未保存修改的面板自动载入；有未保存修改的面板只显示提示条（对比 / 载入外部版本），编辑内容保留 |
| 不冲掉未保存编辑 | 适配器新增 `handlesFileChanges: true`：宿主不再因 mtime 变化重建这类视图；未保存内容随时存成草稿（插件存储），关闭标签/退出/崩溃后再打开会恢复并提示 |
| 编码与换行 | 保持 UTF-8 / UTF-8 BOM / UTF-16LE 与 CRLF。**第 9 轮起 GBK/GB18030 和 UTF-16BE 也可以编辑**（主进程用 iconv-lite 解码和编码），保存时保持原编码；只有能按原编码逐字节还原的文件才允许编辑，否则仍为只读并说明原因。超过 4 MB 或含二进制的文件仍是只读。编辑器工具栏（`editor-encoding`）和底部状态栏（`status-encoding`）显示当前文件的编码和换行方式 |

**将来替换**：`FileOpsBackend`（stat / readBytes / writeBytes{expectedHash} / history / undoWrite）就是 @kb/fileops 需要提供的最小面；接入 @kb/plan 后 `writeBytes` 改成“生成单步计划 → 用户在界面批准（保存确认框就是批准界面）→ 服务层自动执行”，见 docs/08。

**测试**：`tests/text-edit.test.ts`；`e2e/e2e-edit.mjs`（22；第 9 轮改为：Ctrl+S 直接保存后可撤销、.txt 用“保存前预览”开关、GBK 可编辑并按 GBK 写回、状态栏显示编码、撤销后字节一致。新截图 `verify/edit-gbk-encoding.png`）。截图：`verify/edit-save-diff.png`、`verify/edit-conflict-dialog.png`、`verify/edit-conflict-compare.png`、`verify/edit-external-change-banner.png`、`verify/edit-markdown-split.png`。

## D. 冷启动分级加载

**只在面板内容加载这一层做**：dockview 布局序列化结构、布局数据格式（schema 4）、条目格式都没改（e2e 断言启动前后保存的 dock JSON 与条目逐字节相同）。

- 布局照常完整恢复（标签、分栏、尺寸、每个条目的阅读状态）。
- `ViewHost` 里：面板第一次可见时才挂载内容（适配器视图、读文件、渲染 PDF）；后台标签只画一个轻占位，标签带 `data-lazy="pending"`。
- 切到后台标签 → 立即加载，阅读位置照常从条目状态恢复。
- 空闲加载：“可见内容加载完成”之后，等 `settings.backgroundLoadDelayMs`（默认 4000 ms，第 9 轮产品决定保持 4 秒；设成 -1 = 只在切换时加载），再用 `requestIdleCallback` 一个一个加载。
- 网页条目（renderer 'always'）不延后。
- 收起成气泡的面板（自由窗口，见 docs/11）按后台标签处理：启动时不挂载、不计入“可见内容”；点气泡恢复时立即加载（`panelManager.primeCollapsed` 在 `fromJSON` 前记下将被收起的面板，`isHiddenForLoad` 供 `ViewHost` 判断）。
- 不调整进程优先级。
- 适配器新增可选字段 `reportsReady`：内置阅读器在内容画好后调用 `props.reportReady()`。其他视图在挂载后的下一帧就算就绪。
- `startup-trace.json` 的 `summary` 有三个指标：`windowShownMs`（窗口出现）、`interactiveMs`（可交互）、`visibleContentLoadedMs`（可见内容加载完成）。15 s 超时时记 `visibleContentTimedOut`。文件要等“对账扫描完成”和“可见内容加载完成”都到了才写出。
- `scripts/measure-startup.mjs` 输出这三个指标的中位数，测量用的工作区里含一个后台标签。

**测试**：`e2e/e2e-lazy.mjs`（12 项，含“分级加载 + 收起成气泡”3 项）。截图：`verify/lazy-startup.png`、`verify/lazy-after-switch.png`、`verify/lazy-collapsed-restored.png`；计时：`verify/startup-trace-lazy.json`。
