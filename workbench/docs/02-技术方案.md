# 02 技术方案

## 1. 总体架构

```
┌───────────── Renderer（React + dockview，sandbox + contextIsolation）─────────────┐
│ 插件宿主（adapters/panels/commands/chrome·reading·layout 注册表）· 条目宿主 ViewHost │
│ 内置：builtin.workbench、builtin.readers（file 适配器）；主题包 kb.theme.study/pro/bright│
│ 演示第三方插件 demo.csv-table（file 适配器，未隔离）                                  │
└───────────────▲ window.kb（preload 白名单 IPC）          ▲ kbfile://（只读文件流）──┘
                │                                          │
┌───────────────┴──────────── Main（只做编排）──────────────┴──────────────────────┐
│ WorkbenchService（唯一服务层：roots / resources / favorites / layout / ops / search）│
│ RootWatchers（chokidar，去抖批量）  protocol.handle('kbfile')（路径校验）            │
│ [下一轮] Agent 网关：127.0.0.1 HTTP JSON-RPC + token；MCP server 包装同一服务       │
└───────────────┬──────────────────────────────────────────────────────────────────┘
                │ postMessage（任务 / 进度 / 取消）
┌───────────────┴────────── Index Worker（worker_threads）─────────────────────────┐
│ 对账扫描 · 事件应用 · 重命名识别 · 内容哈希 · [下一阶段] 正文抽取（txt/md/PDF）→FTS5 │
│ 独立 SQLite 连接（WAL）                                                            │
└──────────────────────────────────────────────────────────────────────────────────┘
SQLite（better-sqlite3）、blobs/（内容寻址备份）、staging/（删除暂存）都在 app userData
```

## 2. 关键决策与理由

| 决策 | 理由 | 主要风险 / 缓解 |
|---|---|---|
| Electron + TS + React + Vite（主进程/预加载用 esbuild 打包） | Windows 上成熟；Chromium 自带 PDF/图片/字体渲染；pdf.js 生态；迭代快、易打包 | 体积（zip ≈155 MB）与内存；重活放 worker，主进程只编排；PDF 页面按需渲染、离屏释放 |
| 布局用 **dockview**（`dockview-react` 8.x） | 自带标签、拖拽分栏、分隔条、`toJSON/fromJSON` 序列化 | 大版本升级可能改序列化格式 → 布局 JSON 带版本，恢复失败时退回空布局（已 try/catch） |
| SQLite：**better-sqlite3 13**（N-API 预编译，含 `win32-x64.node`） | 同步 API 简单、快；FTS5（trigram 支持中文子串）；N-API 跨 Node/Electron ABI 稳定，**无需针对 Electron 重编译，交叉打包 Windows 直接带预编译二进制** | 要求 Node ≥22：单元测试用 Electron 自带 Node 运行（`ELECTRON_RUN_AS_NODE`）；若未来某版本无预编译，备选 `node-sqlite3-wasm` |
| 索引在 **worker_threads** 中执行 | 遵循“主进程不做重活”；扫描期间 UI 不卡；支持进度和取消 | worker 与主进程两个写连接 → WAL + busy_timeout；后续可把全部写入收敛到 worker |
| 监听：**chokidar 5** + 启动对账扫描 + 手动重新扫描 | 跨平台、成熟；监听只是“加速”，正确性由对账兜底 | 见 §5 |
| 文件读取走 **`kbfile://`** 自定义协议 | 渲染进程不拿任何绝对路径；每次请求都在主进程校验 | 见 §4 |
| **一切皆扩展点**：阅读器、面板、命令、主题经同一 PluginApi 注册，内置功能是内置插件 | 证明 API 足够用；第三方插件与内置功能同等能力；布局与具体实现解耦 | API 过早冻结 → 0.x 期间允许破坏、`engines` 校验；第三方隔离尚未实现（§11.7） |
| 设计令牌 + 受限 CSS 的主题包（纯数据，三轴） | 主题切换零重渲染成本；主题外包无需改核心代码；外框与阅读区可任意组合 | 受限 CSS 由宿主解析校验（见 05）；第三方 iframe 视图需注入令牌 |
| 工作区 = 条目 + 面板（面板只引用 itemId） | 文件/网页/本机应用统一放置与恢复；兼容性逻辑全在适配器，核心只编排 | 条目与布局存在同一 JSON（单写入点、原子保存）；以后若需跨工作区共享条目再拆表 |
| 服务层不依赖 Electron | 同一份代码供 UI、Agent 网关、测试使用 | — |

## 3. 数据模型（`workbench.db`，user_version 迁移）

| 表 | 关键列 | 说明 |
|---|---|---|
| `roots` | `id` UUID PK, `name`, `created_at` | 逻辑根，**不含路径** |
| `root_mounts` | `root_id` PK→roots, `local_path`, `machine_id`, `updated_at` | **机器本地**的挂载点；迁移 = 改这一行（`remapRoot`） |
| `resources` | `id` UUID PK, `root_id`, `rel_path`（`/` 分隔，根为 `''`）, `rel_path_key`（小写）, `name`, `ext`, `kind` file/dir, `size`, `mtime_ms`, `file_key`（Windows: 卷序列号:NTFS 文件索引；其他: dev:ino）, `content_hash`（≤4 MB 文件 sha256）, `missing_since`, UNIQUE(root_id, rel_path) | **路径不是身份**：位置可变，ID 稳定 |
| `resources_fts` | FTS5(trigram)：`resource_id`, `root_id`, `rel_path`, `name` | 文件名/路径搜索；下一阶段增加 `content_fts(resource_id, page, text)` |
| `favorites` | `id`, `resource_id` UNIQUE→resources, `label`, `sort_order` | 引用资源 ID |
| `layout` | `key` PK, `json`, `updated_at` | 全局 UI：`ui`（目录展开的资源 ID、外观 `{chrome, reading, scheme}`）、`window`、`currentWorkspace`；第二轮的 `dock` 在首次启动第三轮时迁入“默认工作区”；**写入时拒绝含绝对路径的 JSON** |
| `workspaces`（v3） | `id` UUID PK, `name`, `project`（分组，可空）, `layout_json`, `layout_schema`, `created_at`, `updated_at`, `last_opened_at` | 命名工作区（全局，可跨根）。`layout_json` 见 §10：条目 + dockview 布局 + 侧栏宽度；保存时检查 schema、≤512 KB、无绝对路径 |
| `op_log` | `id`, `ts`, `actor`（user / agent:名称）, `op`（trash/write/move/undo）, `resource_id`, `root_id`, `rel_path`, `detail_json`, `undone_at` | 每个应用发起的修改 |
| `blobs` | `hash` PK, `size` | 内容寻址备份库索引（文件在 `blobs/<前2位>/<sha256>`） |
| `plugins`（v2） | `id` PK, `version`, `source` builtin/user, `enabled`, `granted_json`（已授权的、规范化的带范围权限）, `installed_at` | 插件状态；升级不改变启用状态 |
| `plugin_kv`（v2） | PK(`plugin_id`, `key`), `value_json`（≤1 MB） | 插件私有存储命名空间；禁用保留、卸载可选删除、随备份导出 |
| `index_state` | `root_id`, `last_scan_at`, `last_error`, `file_count` | 状态栏 |
| 下一阶段 | `notes(id, resource_id?, body, …)`、`tags`、`resource_tags`、`links(src_resource_id, dst_resource_id, anchor_json)`、`content_fts` | 全部引用资源 ID；锚点存页码/文本引用而不是偏移路径 |

**资源身份识别规则**（`indexer.upsertSeen`，监听事件与对账扫描共用）：
1. 同根同路径已有记录 → 复用（编辑器“写临时文件再替换”会换 inode，但路径连续）。
2. 同根内 `file_key` 相同且旧路径已不存在 → 重命名/移动。
3. 回退：同 kind/size/mtime 且旧路径已不存在，若有哈希则必须一致，候选唯一 → 重命名/移动。
4. 否则新建。删除只标记 `missing_since`（收藏显示“失联”），保留 30 天后且无引用才清理。
- 事件批次中先处理新增再处理删除，兼容“先 add 后 unlink”与“先 unlink 后 add”两种顺序。
- 已知盲区：跨根移动被视为“删除 + 新建”（下一轮可在全局 missing 池中按 file_key/hash 匹配）；跨卷移动 file_key 会变，依赖 size+mtime+hash。

## 4. 安全：路径校验（`paths.ts`）

- 相对路径规范化：统一 `/`；拒绝 `..`、盘符、UNC、NUL、含 `:` 的段（NTFS ADS）。
- 解析后必须在根内（Windows 大小写不敏感比较），再对**目标或其最近存在的祖先做 realpath**，挡住根内符号链接/junction 指向根外。
- `kbfile://res/<resourceId>/<name>` 与 `kbfile://root/<rootId>/<rel>`；解码后的段中再出现 `/` 或 `\`（`%2F`、`%5C`）直接拒绝；未注册根拒绝；越界返回 403。
- 注册根时拒绝：与已有根重叠、包含或位于应用数据目录。
- 渲染进程：`sandbox`、`contextIsolation`、CSP、禁止导航与新窗口；Markdown `html:false` + DOMPurify。

## 5. 主要风险

| 风险 | 说明 | 缓解（已做 / 计划） |
|---|---|---|
| Windows 路径 | 大小写不敏感、`\` 分隔、盘符/UNC、260 字符限制、保留名（CON、NUL…）、尾随点/空格 | 元数据统一 `/` + `rel_path_key` 小写；路径校验已按 win32 语义单测；Electron/Node 对长路径一般可用，但需在真实 Windows 上验证 >260 字符路径（T9 验收项）；保留名在写操作中拒绝（待做） |
| 大小写重命名 | `A.md → a.md` 在 NTFS 上是同一文件 | file_key 匹配可识别；需 Windows 实测 |
| 监听可靠性 | 网络盘/SMB 通常收不到通知；超大目录句柄与内存开销；休眠唤醒丢事件；杀毒软件锁文件 | 对账扫描兜底（启动 + 手动 + 计划：定时/唤醒后）；网络盘改为轮询或仅对账；超大根可配置忽略规则；状态栏显示“未监听” |
| better-sqlite3 原生模块 | Windows 需匹配架构的二进制 | 13.x 自带 N-API 预编译（已确认打包进 `app.asar.unpacked/.../win32-x64.node`，PE x64）；`npmRebuild:false` 避免交叉编译；**需真机验证可加载** |
| PDF 内存 | 大 PDF 多标签并开会占用大量内存 | 页面按视口渲染、离屏释放 canvas、关标签 `destroy()`；计划：限制同时渲染的页数、缩略图缓存 |
| 根重新映射 | 换电脑后路径不同 | 元数据不存绝对路径；`remapRoot` 后对账扫描按路径复用资源 ID（已测：复制到新位置 inode 全变仍保持 ID/收藏/布局） |
| Agent 写入 vs 用户编辑冲突 | Agent 覆盖用户正在编辑的文件；用户在 Agent 之后又修改 | 写前备份原内容；撤销前比较 `afterHash`，不一致则报冲突，“保留两者”时先备份当前内容再还原（已实现并测试）；计划：写入前 `expectedHash` 乐观锁、对打开中的标签提示外部修改 |
| 两个 SQLite 写连接 | 主进程（listDir/收藏/操作）与 worker | WAL + busy_timeout 5s；后续将写入集中到 worker 或单写队列 |

## 6. 文件修改与恢复设计（服务层已实现）

- **删除** = 移到应用暂存区 `staging/<uuid>/<name>`（跨盘自动 copy+delete），**不使用系统回收站**（系统回收站对应用不可编程恢复、不可预览）。默认保留 30 天（`purgeStaging`）。
- **覆盖写** = 原内容先进入内容寻址备份库 `blobs/`，再临时文件 + rename 原子替换；`op_log` 记录 `beforeHash/afterHash`。
- **移动/重命名** = 记录 `from/to`，直接更新资源位置（ID 不变）。
- **预览**（`previewTrash/previewWrite/previewMove/previewUndo`）：影响文件数、字节数、说明、冲突列表。
- **撤销**：默认遇冲突报错；`keep-both` 恢复为“名称 (恢复 N).ext”或先备份当前内容再还原；撤销本身也记入 `op_log`。

## 7. Agent 接口草案（下一轮实现，本轮只留接缝）

- 进程内：`WorkbenchService` 已与 Electron 解耦，Agent 网关直接调用它。
- 传输：主进程内 HTTP JSON-RPC 2.0，**只绑定 127.0.0.1**，随机端口写入 `userData/agent-endpoint.json`；每次启动生成 token（Bearer），文件权限仅当前用户；拒绝带 `Origin` 的浏览器请求（防 DNS rebinding/CSRF）。
- MCP：独立 `kb-mcp` 小进程（stdio），读取 endpoint + token 后转发到 JSON-RPC。
- 方法（全部以 rootId + relPath 或 resourceId 为参数，**所有路径都经 §4 校验，包括解析符号链接/junction、Windows 大小写不敏感**）：

| 方法 | 说明 |
|---|---|
| `roots.list` | 列出授权根 |
| `fs.list(rootId, relPath)` / `fs.stat` / `fs.readText(resourceId, range?)` | 只读 |
| `search(query, {content?})` | 文件名/正文 |
| `ops.preview{Write,Move,Trash}` | 返回预览与冲突 |
| `fs.write(resourceId or rootId+relPath, content, {expectedHash})` / `fs.move` / `fs.trash` | 执行；`actor = agent:<name>`；是否需要逐次人工批准见“待决策” |
| `ops.list` / `ops.undo(opId, onConflict)` | 恢复 |
| `notes.*` / `links.*` | 下一阶段 |

- 每个 Agent 有名称与权限范围（可读根、可写根）；写操作全部进入 `op_log`，UI 可按 actor 筛选与批量撤销。

## 8. 构建与打包

- `npm run build`：esbuild 打包 `out/main/{index,indexWorker}.js`、`out/preload/index.js`；Vite 打包 `out/renderer`。
- `electron-builder --win zip`（或 `portable`）：`npmRebuild:false`，`asarUnpack` better-sqlite3，Windows 包内只保留 `win32-x64.node`。运行时依赖只有 better-sqlite3，其余前端库已被打包进 bundle（放在 devDependencies）。
- **本轮在 Linux 上交叉打出的 Windows 产物未在 Windows 上运行过，不能作为“Windows 可交付”的证据**；验收必须在真实 Windows 10/11 上完成（03 T9）。


## 9. 视觉设计系统

完整接口见 [05-主题接口.md](05-主题接口.md)（第三轮重写）。要点：

- **三个独立的轴**：外框样式（chromeThemes）、阅读区样式（readingThemes）、布局预设（layoutPresets）。外框与阅读区可任意组合（如“B 外框 + A 阅读区”），每个样式必须同时提供 light 与 dark；明暗另作一项选择（浅色/深色/跟随系统）。
- **令牌**：主题接口 1.0 共 105 个 `--kb-*` 令牌（外框 80、阅读区 25），单一来源 `src/shared/theme-contract.json`（`scripts/gen-theme-contract.py` 生成），核心 `styles.css` 只引用这些令牌（有单元测试保证“用到的都已声明、声明的都被用到”）。
- **组件状态**：15 个组件 × default/hover/active/focus/disabled/selected/drag-over，每个组件有可被主题选择的钩子类。
- **主题包是纯数据**：`theme.json` + 受限 CSS + 布局预设 JSON。宿主解析 CSS：只允许以钩子类开头的选择器、禁止布局属性/外部资源/改写变量，并自动加作用域前缀 `:root[data-kb-chrome=…][data-kb-scheme=…]`。
- **切换外观不改变布局与进度**：尺寸令牌只影响外观，分栏间隙用分组内边距实现，不改变保存的分栏比例；Markdown/文本以“阅读锚点”保持视口顶部的段落；PDF 以页码 + 页内位置保持（E2E 验证）。
- dockview 自带变量（`--dv-*`）统一映射到 `--kb-*`。

## 10. 工作区与条目模型（第三轮实现）

### 10.1 数据结构（布局 schema 4 + `workspace_items` 表，第四轮）

```ts
interface WorkspaceLayout {
  schema: 4;
  dock: SerializedDockview | null;        // dockview toJSON；每个面板 params 只有 { itemId }
  shell: { sidebarWidth: number };
}
// 表 workspace_items(workspace_id, item_id, source_kind, adapter_id, ref, display_mode, state_json, title, created_at, updated_at)
interface WorkspaceItem {
  itemId: string;
  sourceKind: 'file' | 'web' | 'app';
  adapterId: string;                      // 适配器 id（'auto' = 旧布局迁移而来，首次打开时按优先级固化）
  ref: string;                            // file: resourceId；web: URL；app: appProfileId
  displayMode: 'in-app-reader' | 'in-app-web' | 'external-managed';
  state?: { v: number; data: unknown };   // 版本化、小（≤16 KB）、无秘密、无文件内容
  title?: string;
}
```

- **条目单独存表**（SDK H1）：第三轮的 schema 3 把条目内联在布局 JSON 里；第四轮 DB 迁移 v4 把它们拆进 `workspace_items`，布局升为 schema 4（详见 06 §2）。保存接口 `saveWorkspaceLayout(id, layout, items)`，服务层逐条校验并删除不再被引用的条目。
- **面板只引用 itemId**：dockview 中所有面板都是同一个通用组件 `view`（条目宿主 `ViewHost`），参数只有 `{itemId}`；从不出现阅读器类名、组件名或路径。
- **保存**（`toStoredLayout`）：面板参数只保留 itemId；丢弃没有面板引用的条目；状态剔除疑似秘密的键（SDK `checkStateForSave` 规则）；单条状态超过 16 KB 时丢弃（回到默认状态）；web 引用用 SDK `sanitizeUrlForState`（只保存 http(s)，去掉账号密码与查询串，保留 `#` 片段）；整个布局 ≤ 512 KB；服务层再次拒绝绝对路径。
- **迁移**（`migrateLayout`）：v1（第一轮 `component:'file'`）与 v2（`{viewType, resourceId, state}`）的每个面板变为一个 file 条目，itemId 沿用旧面板 id，状态包成 `{v:1, data}`；v3 的内联条目拆出；所有版本都剪掉引用了不存在条目的悬空面板。打开旧版本工作区后立即按 v4 保存。schema 高于本版本 → 以只读横幅提示，**不覆盖**。
- **视图状态 vs 插件设置**：每个面板的状态属于工作区；插件的全局设置存 `plugin_kv`，不随工作区切换。
- **状态版本**：适配器声明 `stateSchemaVersion`；恢复时同版本直接使用，旧版本交给适配器的 `migrateState`，没有迁移函数或版本更新则丢弃（回到默认状态）。第三方沙箱插件在 iframe 内用 SDK `restoreFromEnvelope` 处理。

### 10.2 核心职责（只编排）

核心只做：把条目放进布局、启用/禁用插件、恢复状态、在不能显示时给出占位。占位种类与 SDK `PlaceholderKind` 一致（第四轮起，T22），文案与动作来自 SDK `placeholderFor`：

| 种类 | 何时 | 主要动作 |
| --- | --- | --- |
| `phase-unavailable` | 来源类型在本阶段未开放（web、app） | 从工作区移除 |
| `adapter-missing` | 适配器未安装（含卸载但保留条目） | 安装插件… / 用内置阅读器打开（仅本次） / 移除 |
| `adapter-disabled` | 提供适配器的插件已禁用 | 启用插件 / 用内置阅读器打开 |
| `adapter-incompatible` | 插件不兼容（engines、manifest 校验失败） | 用内置阅读器打开 / 移除 |
| `permission-denied` | 未授权、已拒绝、已撤销，或文件不在授权的根/扩展名内 | 查看权限… / 移除 |
| `resource-missing` | file 条目的文件不在了 | 重试 / 移除 |
| `adapter-error` | 沙箱激活/打开失败、15 秒未就绪 | 重试 / 用内置阅读器打开 |
| `domain-blocked` / `network-offline` | P2 网页面板（条目地址不在允许域名内 / 主框架加载失败） | 用系统浏览器打开（仅 https，需确认）、回到首页、从工作区移除 |
| `app-not-installed` / `app-verification-failed` | P3 才会出现 | 文案就绪，动作暂为禁用 |

判定顺序与动作行为见 06 §7。占位**不改写**条目的 adapterId 与状态，条件恢复后自动复原；“用内置阅读器打开”只对本次显示生效；其他面板不受影响。

### 10.3 工作区的保存、切换与导出

- 改动（标签、分栏、尺寸、侧栏宽度、条目状态）在 300 ms 内自动保存；**切换工作区、导出、退出前先写完**（`flush`）。退出：主进程拦截窗口关闭 → 通知渲染进程写完 → 收到确认后关闭（3 秒超时保护）。第二轮的 150 ms 去抖丢失问题由此修复；阅读器的位置上报改为每帧一次（不再有去抖延迟）。
- 当前工作区 id 存在 `layout.currentWorkspace`；首次运行创建“默认工作区”并迁入第二轮保存的布局。删除只删布局记录，至少保留一个工作区。
- 导出 `.kblayout.json`：`{format:'kb-workbench.layout', formatVersion:1, exportedAt, workspace:{name, project}, layoutSchema, layout, resources:[{resourceId, rootId, rootName, relPath, kind}]}`。只有 file 条目引用资源；不含绝对路径、不含文件内容。
- 导入：资源 id 在本机存在则直接使用；否则按根 id、再按根名（唯一时）+ 相对路径匹配本机资源并替换 id；仍匹配不到的保留原 id（打开时“文件不可用”）。重名自动加“(2)”。web/app 条目原样导入。
- 布局预设（`applyPreset`）：现有分组按顺序放入 slot 1..n，多出的并入最后一个 slot，空 slot 去掉；只改网格，不改条目与状态。

## 11. 插件架构

### 11.1 扩展点

| 扩展点 | API | 说明 |
|---|---|---|
| 适配器 | `adapters.register({ id, title, sourceKinds, displayMode, match(target)→优先级, component, stateSchemaVersion?, migrateState?, serializeState?, restoreState? })` | 决定“某个条目如何显示”。`target` 为 `{sourceKind:'file', resource}` / `{sourceKind:'web', url}` / `{sourceKind:'app', appProfileId}`；优先级：内置 100、回退 1、插件可用 200 覆盖；`match` 抛异常视为 0。`views.register` 保留为只注册 file 适配器的废弃别名 |
| 面板 | `panels.register({ id, title, location: 'sidebar' \| 'bottom', order, component })` | 侧栏/底部面板 |
| 命令 | `commands.register({ id, title, category, keybinding, run })` / `commands.execute(id)` | 命令面板（Ctrl+Shift+P）与快捷键 |
| 外观 | `themes.registerChrome / registerReading / registerLayoutPreset` | 主题包由宿主转成插件后调用，见 05 |
| 下一批 | 搜索提供者、正文抽取器（worker 中）、文件操作钩子、笔记块类型、导出格式 | |

宿主能力：内置插件用 `workspace.readText / fileUrl / rootFileUrl / showInFolder`、`storage.get/set/delete/keys`。第三方沙箱插件用 SDK 的 `ReaderContext`：`files.stat/readText/readBytes/contentUrl/onDidChange`（按授权根与扩展名检查）、`files.requestFileops`（批量计划 → 用户批准 → 经 fileops 执行并写操作记录）、`storage.*`、`permissions.request`（见 06）。

{

  "version": "0.2.0",

      "match": { "extensions": ["csv"] }, // 静态声明（用于未激活前的“打开方式”）；运行时以 match() 为准

    "panels": [], "commands": [], "chromeThemes": [], "readingThemes": [], "layoutPresets": []

### 11.3 生命周期
1. **安装**：第三方适配器插件只能在开发者模式下从本地文件夹安装到 `userData/plugins/<id>/`（第四轮，见 06 §3；`.kbplugin` 包与签名不做，D7）；校验 SDK manifest 与 `engines`；不兼容则安装但不激活并显示原因。主题包可从文件夹安装到 `userData/themes/<id>/`。
2. **授权**：第一次打开需要某个权限的条目时，按“插件 + 适配器 + 权限”逐项询问（`fs.read` 可按根勾选），记录在 `plugins.granted_json`（`PermissionGrant[]`，含 `declHash`）；拒绝会被记住，相关条目显示 `permission-denied` 占位；插件管理里可逐项撤销或改为允许。
3. **激活**：`activate(api)` 抛错 → 状态“出错”，撤销其已注册的全部贡献，不影响其他插件。按 activationEvents 懒激活尚未实现。
4. **运行时崩溃隔离**：每个视图包在 ErrorBoundary 中；第三方插件在沙箱 iframe 中运行，激活/打开失败、超时或被看门狗判定卡死（3 秒无心跳，插件 iframe 在独立进程中，卸载后进程结束）→ `adapter-error` 占位、可重试；拒绝、计划、看门狗写入审计记录（见 06 §5.2–5.3）。
5. **停用/禁用**：宿主统一回收注册项；打开中的视图变占位；**数据保留**。
6. **卸载**：卸载对话框（06 §8）：保留/删除数据，列出存储、授权与网站数据，可选“同时从工作区移除其条目”（默认保留为占位）；内置插件不可卸载只可禁用。
7. **升级**：同 id 重新安装 = 升级，启用状态、授权与存储保留；某项权限声明变化（`declHash` 不同）→ 该项重新询问。

### 11.4 权限模型（结构化、带范围，由用户批准；第四轮以 SDK 为准）

| 权限 `kind` | 声明 | 含义 | v1 第三方 |
| --- | --- | --- | --- |
| `fs.read` | `scope: 'ask-per-root' \| 'all-registered-roots'`，`extensions[]` | 只能经宿主读取授权根内、指定扩展名的资源；拿不到绝对路径；`kbfile://plugin/<令牌>` 每次请求按当前授权检查 | 允许 |
| `fileops.write` | `operations: ('write'\|'move'\|'trash')[]` | 只能提交批量计划，用户逐步看过后批准，经 fileops 执行、写操作记录、可撤销 | 允许（每次计划都要批准） |
| `net` | `domains[]`（不允许 `*`、IP、localhost） | 网页面板只能访问列出的域名 | **不允许**（P2） |
| `process.launch` | `programs[{path, sha256?}]` | 只能启动指定的程序 | **不允许**（P3） |

- 类型与校验直接用 SDK 的 `types.ts`/`policy.ts`（副本，提交 050df08，见 06 §1）。旧的字符串写法（`fs:roots` 等）不再接受；第三轮保存的字符串授权在 DB v4 迁移时清空，内置插件的 manifest 已改写为结构化。
- 授权记录 `PermissionGrant{pluginId, adapterId, permissionId, decision, rootIds?, declHash, decidedAt}`；`declHash` = `permissionDeclHash(声明)`，由主进程计算。声明一变即视为未询问。
- 必需权限在打开条目时询问；`optional: true` 的在插件请求时询问。

### 11.5 版本兼容
- 宿主 API 版本 `HOST_API_VERSION` 当前 **0.2.0**（第三轮：views→adapters、themes 三轴；0.1 插件需要把 `engines` 改为 `^0.2.0`，`views.register` 仍可用）。0.x 期间次版本即可能破坏；1.0 起只在主版本破坏。
- 主题接口单独版本化：`themeContract` 1.0.0（见 05）。
- 不兼容插件（`engines` 不满足、未知或无范围权限、显示方式与来源类型不符、非法 id/版本）自动禁用并在插件面板显示原因。

### 11.6 数据保留
插件数据只存在应用数据目录：`plugin_kv`（按插件 id 隔离）以及将来的 `userData/plugin-data/<id>/`；禁用保留、卸载询问、随元数据库备份一起导出。工作区中条目的状态属于工作区，不随插件删除。

### 11.7 隔离方案与风险
| 插件类型 | 运行位置 | 理由 | 风险 |
|---|---|---|---|
| 内置（readers/workbench） | 渲染进程，与宿主同一 React 树 | 性能最好；代码可信 | 内置插件 bug 可能拖垮 UI（ErrorBoundary 缓解） |
| 主题包 | 不执行代码：宿主读取 JSON 与受限 CSS | 主题外包无需代码权限 | CSS 解析器需持续加固（见 05 §6） |
| 第三方适配器插件（v1 唯一的第三方类型） | **沙箱 iframe**（`sandbox="allow-scripts"`，null origin，`kbplugin://<id>/` 提供代码，CSP 禁网络；独立渲染进程），postMessage RPC 调用宿主 API；界面以 UiNode 树交给宿主用文本节点渲染 | 隔离 DOM/全局对象与 CPU；权限在主进程检查 | 自绘界面（pdf.js 等）暂不支持；RPC 延迟；无内存配额 |
| 第三方后台逻辑 | v1 不提供；以后用 `utilityProcess` | 产品决定 | — |

v1 第三方插件的安装来源只有本地文件夹（开发者模式），没有商店与签名（D7）。

**说明**：演示插件 `demo.csv-table` 现在标为内置（随应用打包、在渲染进程运行），但仍按结构化 `fs.read` 走授权。真正的第三方隔离由沙箱 iframe 提供，见 06；端到端用例用 SDK 的 file-adapter 模板（JSON 查看器）和恶意测试插件验证。

## 12. 来源类型、适配器与分阶段路线

### 12.1 分阶段

| 阶段 | 内容 | 本轮状态 |
| --- | --- | --- |
| P1 | 文件阅读器 + 工作区面板：file 条目端到端（打开、保存、恢复、迁移、导出导入、占位）；第三方沙箱适配器（H1–H8） | ✅ 完成（Linux 自动化验证；Windows 未验证） |
| P2 | 网页面板：web 适配器，按插件隔离的会话分区、只允许声明的域名、用户批准 | ✅ H9 完成（第六轮，Linux 自动化验证；Windows 未验证；见 06 §11） |
| P3 | 指定的本机应用适配器：逐个程序接入（程序路径/哈希、参数模板），外部程序在独立窗口中运行 | 只有类型、校验与“暂不可用”占位 |

当前阶段 `CURRENT_PHASE = 2`：file、web 可用，app 未开放。未开放的来源类型不弹授权、不加载适配器，条目原样保留。

### 12.2 诚实的显示方式

| 来源 | 唯一允许的 displayMode | 面板里显示什么 |
| --- | --- | --- |
| file | `in-app-reader` | 适配器在应用内渲染的阅读器 |
| web | `in-app-web` | 宿主管理的受限网页面板（仅限声明域名） |
| app | `external-managed` | 外部程序的状态与控制（启动、切换到窗口）；程序本身在应用之外的独立窗口中运行 |

- manifest 校验与运行时注册都强制这一对应关系（`checkDisplayMode`），适配器不能声称“嵌入”。
- **不保证任意 Windows 程序可以嵌入面板**：跨进程父子窗口会共享输入队列（一方卡死另一方也卡）、DPI 不一致、焦点/输入法/快捷键冲突、管理员权限与 UWP 程序无法嵌入、程序会重建或多开窗口。若将来开放嵌入，只能作为实验选项，**每个程序、每个版本单独验证**（验收清单见 `kb-adapter-sdk/docs/适配器规范.md` §7），验证不符时自动回落为 external-managed。
