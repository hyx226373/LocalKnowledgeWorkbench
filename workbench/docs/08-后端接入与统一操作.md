# 08 后端接入与统一操作入口（第 9 轮 E）

> 目标：磐石组的 `@kb/plan`、`@kb/fileops`、`searchGrouped`、`createSync` 验收后，**一处替换**即可接入；
> 界面和 agent 走**同一个操作入口**，区别只在“谁能批准”。
> 状态（第 10 轮）：已接到真实 `@kb/*`（经适配层）。IPC / 待批准 UI / loopback agent 已开放。
> 契约测试含 mock、LocalPlan、`@kb/plan`；e2e `e2e-plans.mjs` 覆盖批准全流程。
> **已知缺口**：主库与 identity-watch/fileops 表结构不兼容，@kb 栈用独立 `kb-modules/modules.sqlite`；TextEdit 仍走 LocalFileOps。

## 1. 总体结构

```
 界面（渲染进程）                          agent（将来：本地进程 / 插件 / MCP）
   │ IPC，channel = 'ui'                     │ channel = 'agent'
   ▼                                         ▼
 ┌──────────────── OperationService（src/main/backend/operations.ts）────────────────┐
 │  forUi()    → { propose, get, approve, pending }                                  │
 │  forAgent() → { propose, get }        ← 门面上根本没有 approve                       │
 │  propose：把“写入/移动/移到废纸篓…”整理成计划；write 的新内容先暂存，计划里只放哈希      │
 └───────────────────────────────┬───────────────────────────────────────────────────┘
                                 ▼
 ┌──────────────── PlanGateway（src/main/backend/plan.ts）────────────────────────────┐
 │  我方二次校验（不依赖对方是否已实现）：                                               │
 │   ① 只有 channel='ui' 能批准      ② 批准绑定 contentHash，计划改过 → stale 拒绝         │
 │   ③ 只能批准 draft、只能批准计划里存在的 opId、不能空批准                              │
 │   ④ 批准成功后立即 applyPlan（服务层自动执行，调用方不再单独“执行”）                    │
 └───────────────────────────────┬───────────────────────────────────────────────────┘
                                 ▼
   KbPlanService 接口  ── 现在：KbPlanAdapter(@kb/plan)（planAdapter.ts）；LocalPlanService 作契约/兜底
                                 ▼
   FileOpsBackend 接口 ── TextEdit：LocalFileOps（主库 op_log）
                       计划执行：@kb/fileops（modules 栈）
   每一步写 op_log（actor = 'user' | 'agent:<名字>'，detail.planId），撤销沿用现有 undo。

 搜索：SearchBackend.search(q,{limit,rootIds}) → GroupedResult
        现在 HybridSearch(KbSearch(searchGrouped) + LocalSearch)   （search.ts）
        normalizeGrouped：rootIds 过滤、每条 matches ≤ 3（matchesTruncated）、limit 截断（truncated）
 同步：SyncBackend.startSync(rootId) → SyncHandle { onProgress, cancel, whenIdle, done }
        现在 KbSync(createSync) + 主库 startIndex；LocalSync 兜底   （sync.ts）
        guardHandle 包住对方句柄：done 只结算一次、cancel 幂等、退订后不再回调
```

为什么 agent 不能批准：批准动作只存在于 `forUi()` 返回的对象上，并且 PlanGateway 再按 channel 拒绝一次。
agent 拿到的是 `forAgent(name)`，类型上就没有 `approve`（测试 `'approve' in agent === false`）。
agent 提的计划出现在界面的 `pending()` 列表里，由用户在界面里看预览、勾选、批准。

## 2. 同一个操作在两条路上

| 步骤 | 界面（例如保存编辑） | agent（例如“整理助手”改写文件） |
|---|---|---|
| 提出 | `ui.propose('保存 a.md', [{kind:'write', resourceId, content, expectedHash}])` | `agent.propose(...)`，同样参数 |
| 预览 | 返回 `preview`（每项 summary + conflicts） | 同左；agent 只能看，不能批准 |
| 批准 | `ui.approve(planId, 勾选的 opIds, preview.contentHash)` | 无。等用户在界面批准 |
| 执行 | 批准成功即自动执行 | 同左（由用户批准触发） |
| 记录 | op_log actor=`user` | op_log actor=`agent:整理助手`，detail.planId |
| 撤销 | 现有撤销 | 同左 |

## 3. 文本编辑保存如何并入（C 项衔接）

现在 `TextEditService.save` 直接调 `FileOpsBackend.writeBytes(expectedHash)`；保存前的差异对话框就是“预览 + 批准”界面。并入步骤：

1. `textPreviewSave` → 改为 `ui.propose('保存 <文件名>', [{kind:'write', …, expectedHash}])`，用返回的 preview + 本地 diff 显示对话框；
2. 用户点“保存” → `ui.approve(planId, ['op1'], preview.contentHash)`；
3. 结果 `failed` 且 error 为冲突 → 走现有冲突对话框（保留我的 / 采用外部的 / 对比后再决定）；
4. 编码、BOM、换行仍由 TextEditService 在 propose 之前处理成字节，计划层只看字节和哈希。

渲染进程接口（`textSave` 等）不需要改签名，改动全在主进程。

## 4. 替换步骤（每个模块独立，可分别上线）

**@kb/plan**
1. `npm i @kb/plan`（或 workspace 依赖），在 `src/main/index.ts` 创建 `createPlanService({ db, fileOps })`，启动时调 `migrate()`；
2. 若字段名与 `KbPlanService` 不同，在 `plan.ts` 写一个薄转换层（只改这一个文件）；
3. `new OperationService(svc, realPlans)` 替换 `LocalPlanService`；
4. 在 `tests/backend-contract.test.ts` 加一行 `planContract('@kb/plan', …)`，同一套 5 项用例必须全过；
5. 删除 LocalPlanService 的内存实现（或留作测试替身）。

**@kb/fileops**：实现 `FileOpsBackend`（stat / readBytes / writeBytes(expectedHash) / undoLastWrite / history），替换 `new LocalFileOps(svc)`；`tests/text-edit.test.ts` 6 项照跑。

**searchGrouped**：`new KbSearch(searchGrouped, db)` 替换 `LocalSearch`，IPC `search` 改用 `SearchBackend`；渲染进程按 `GroupedHit.matches[].anchor` 跳转（PDF 用 page，文本用字符偏移）。

**createSync**：`createSync({ db, dbPath, resolveLocalPath }).startSync(rootId)` 外面套 `guardHandle`，替换 LocalSync；状态栏进度、取消按钮接 `onProgress` / `cancel`。

## 5. 第 10 轮已完成 / 仍缺

已完成：真实 `@kb/plan` / `searchGrouped` / `createSync` 装配；agent loopback（仅 propose/get）；待批准 UI；契约 + e2e。

仍缺 / 反馈磐石：
- 主库 `resources`/`op_log` 与 identity-watch/fileops 不兼容，无法同库；需统一 schema 或官方双库约定；
- `@kb/plan` 的 contentHash 是批准 HMAC，与我方 ops 规范化哈希不同（适配层已消化）；
- FileOp 无 `expectedHash` / copy；approve 自动执行（无独立 applyPlan）；
- TextEdit 尚未并入统一计划入口（仍 LocalFileOps 直接写）。


## 索引健康与双库（r11-E）

- `KbApi.getIndexHealth()` / 事件 `kb:index-health`：`IndexHealth { engine, contentSearch, reason?, since, scannedFiles, contentIndexedFiles }`。
- `engine==='local-fallback'` 时状态栏与搜索区显示「全文索引不可用 · 仅文件名/路径搜索」；扫描量与正文索引量分开，不得用「已索引 N」暗示正文可搜。
- `searchGrouped` 结果含 `degraded?: boolean`。
- `KbApi.debugDualDbCheck(rootId?)`：仅开发 / e2e；返回主库与 modules 库 resourceId/路径不一致项。
- 命令：`index.showHealth`、`index.rebuild`。
- **网络正文索引**：本轮不做；A 缓存落地的直链本地文件可按本地路径喂给 indexer（见磐石 REPORT 边界）。
