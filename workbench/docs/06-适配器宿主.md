## 2. 数据（H1）

- **数据库 v4**（`db.ts` 第 4 个迁移，JS 函数）：
  - 新表 `workspace_items(workspace_id → workspaces ON DELETE CASCADE, item_id, source_kind, adapter_id, ref, display_mode, state_json, title, created_at, updated_at, PK(workspace_id,item_id))`，索引 `adapter_id`。
  - `plugins` 重建：`source` 增加 `'adapter'`（第三方沙箱适配器插件），新增 `uninstalled_at`（“卸载但保留数据”）。
  - 把每个 schema 3 工作区的内联 `items` 拆进 `workspace_items`，布局改为 schema 4。schema 1/2 的工作区原样保留，渲染进程打开时迁移后立即按 schema 4 保存。
- **布局 schema 4**：`{schema:4, dock, shell}`，不再含 `items`；dock 中每个面板 `params` 只有 `{itemId}`。条目单独存表。
- **保存**：`saveWorkspaceLayout(id, layout, items)`。主进程校验：schema 4 不能内联条目；每个条目经 `sanitizeItem`（适配器 id、ref 字符集、显示方式、≤16 KB 状态、web 引用用 SDK `sanitizeUrlForState`）；每个面板引用的条目必须存在；整体 ≤ 512 KB；不得出现绝对路径。旧客户端发来的 schema 3 仍可保存（拆表；任何条目不合法则整体拒绝）。保存时项目表中未出现的条目被删除。
- **恢复**：`migrateLayout(layout, legacyShell, items)` 对所有版本都剪掉“引用了不存在条目”的悬空面板（`pruneDock`，空分组一并去掉）。
- **导出/导入**：`.kblayout.json` 的 `layout` 为 schema 4，另带 `items`；导入时按“根名 + 相对路径”重映射 file 条目的 ref。

## 3. 插件包与开发者模式安装（H2，D7）

- **插件包**：一个文件夹，含 `manifest.json`（SDK `AdapterPluginManifest`，`sandbox:"iframe"`）和 `main` 指向的**单文件 ES 模块**（包内相对路径，`.js/.mjs`）。可以带图片等静态资源，按 `kbplugin://<id>/<路径>` 访问。
- **打包**：`npm run plugin:build -- <插件源码目录> --out <输出目录>`（`scripts/build-adapter-plugin.mjs`，esbuild，ESM，浏览器目标）。`@kb-workbench/adapter-sdk[/policy|/types]` 解析到核心内置的 SDK 副本，插件目录不需要 node_modules；`mock-host` 禁止打进插件。
- **安装校验**（主进程 `PluginHostService.readPackage`，不执行代码）：`validateAdapterManifest` 全部规则；`engines.workbench` 满足宿主版本；id 不能以 `builtin.` `demo.` `kb.` 开头，不能与内置插件/主题包重名；每个适配器 id 以插件 id 为前缀；`main` 存在。复制时跳过 `node_modules`、`.git`、符号链接，上限 2000 个文件 / 50 MB。校验失败但 manifest 可读 → 仍安装，显示“不兼容”及原因，不激活。
- **只能开发者模式**：插件管理 →“开发者模式”开关（`layout.settings.devMode`）→“安装本地插件文件夹（开发者模式）…”。主进程在开关关闭时拒绝安装调用。没有商店、签名、自动更新。同 id 再次安装 = 升级/重装，保留授权与存储。

### Windows 上的开发者安装步骤
1. 在任意目录打包插件：`npm run plugin:build -- D:\work\my-json-viewer --out D:\work\my-json-viewer-dist`（SDK 模板：`--` 后写 `<SDK>\templates\file-adapter`）。
2. 打开工作台 → 侧栏“插件”→“管理插件…”（或命令面板“插件管理…”）。
3. 勾选“开发者模式”→“安装本地插件文件夹（开发者模式）…”→ 选择第 1 步的输出目录（含 `manifest.json` 的那一层）。
4. 插件出现在“第三方适配器插件”中，状态“已启用”。打开一个匹配的文件（模板：`.json`）→ 授权对话框 → 勾选允许的文件夹 →“允许”。
5. 插件被复制到 `%APPDATA%\本地知识工作台\plugins\<id>\`（实际以 `app.getPath('userData')` 为准）；改代码后重复 1、3 即可覆盖安装。

## 4. 授权（H2/H3）

- **何时询问**：打开使用该适配器的条目时，对每个**必需**且“未询问/声明已变化”的权限弹一次（同一权限并发打开只弹一个对话框）。`optional: true` 的权限不在打开时询问，由插件 `ctx.permissions.request()` 或首次 `requestFileops` 时询问。
- **授权对话框**（`perm-dialog`）：插件名、适配器名、权限种类、显示方式（`displayModeLabel`）、理由（manifest `reason` 原文）、范围（`describePermission`）、来源“开发者模式安装的本地插件（未签名）”。`fs.read` 的 `ask-per-root` 列出所有已注册根的勾选框：默认只勾“当前文件所在的根”，已授权后再改时预选已授权的根；至少勾一个才能允许。`all-registered-roots` 授权时记录当时的根列表（之后新增的根需要重新授权）。
- **拒绝**：记住“已拒绝”，相关面板显示 `permission-denied` 占位（“查看权限…”/“从工作区移除”），其他面板照常恢复，重启后不再弹窗。
- **插件管理中逐项管理**：每个适配器的每个权限显示状态（已允许：哪些文件夹 / 已拒绝 / 已撤销 / 尚未询问 / 声明已变化）以及“撤销”“改为允许… / 更改文件夹…”。撤销立即生效：渲染进程的面板变为占位，主进程对后续读取一律拒绝（令牌也随之失效，因为每次请求都按当前授权检查）。

## 5. 沙箱运行时（H4）

- **框架**：每个第三方面板一个 `<iframe sandbox="allow-scripts" src="kbplugin://<pluginId>/__kb/frame.html">`（无 `allow-same-origin` → null origin，拿不到父文档、`window.kb`、Cookie/存储）。iframe 本身 1×1 隐藏，只运行代码；界面由宿主用 UiNode 渲染。
- **kbplugin 协议**（主进程）：`__kb/frame.html`（宿主运行页，只有 `<script type=module src="/__kb/runtime.js">`）、`__kb/runtime.js`（`src/plugin-runtime/runtime.ts` 打包产物）、包内文件（越出包目录拒绝）。所有响应带 CSP：`default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src kbfile://plugin data:; font-src 'self' data:; connect-src 'none'; …`，因此插件不能联网、不能 `fetch` 任何 kbfile URL、只能用 `kbfile://plugin/<令牌>/…` 显示图片。`will-frame-navigate`：子框架只能导航到插件宿主运行页，已加载的插件框架不能换成另一个插件。
- **加载**：运行时 `import('kbplugin://<id>/<main>')`（必须是绝对 URL），调用 `activate(api)`，然后 `open(item, ctx)` → `mount(target)`。15 秒内运行时没有就绪 → `adapter-error` 占位（可重试）。
- **UiNode 渲染**：宿主对插件发来的树**重新构造**（`sanitizeUiNode`：只保留已知字段；未知节点类型 → “不支持的界面节点”提示；深度 ≤ 32、节点 ≤ 5000、字符串截断），再用 React 文本节点渲染（等价 textContent；没有 innerHTML/href/src/style 透传）。外观只用主题令牌（`.kb-ui-*` 类），主题切换自动跟随；同时把令牌快照（`ThemeSnapshot`）推给沙箱供自绘内容使用。
- **状态**：插件 `ctx.requestSave()` → 运行时取 `getState()` → 宿主 `checkStateForSave(data, maxStateBytes)`（SDK 规则：≤16 KB、字符串 ≤2048、无疑似秘密键）→ 写入条目 `{v: stateSchemaVersion, data}`。打开时运行时用 `restoreFromEnvelope` 迁移/校验；被重置时面板显示一次“状态已重置”提示。
- **v1 不提供** `ReaderMountTarget.element`（插件自绘 DOM）：iframe 不可见，只有 UiNode。

### 5.1 postMessage 协议（`src/shared/sandboxProtocol.ts`）
消息外形 `{kb:'kb-frame'|'kb-host', type, …}`。宿主只接受 `event.source === 本面板 iframe.contentWindow` 且通过 `parseFrameMessage` 白名单的消息；插件身份取自面板所属插件，消息里的任何身份字段都被忽略。

| 方向 | type | 内容 |
| --- | --- | --- |
| 框架→宿主 | `ready` / `activated` / `activate-error{message}` / `opened{reset}` / `open-error{message}` | 生命周期 |
| 框架→宿主 | `render{node}` / `set-title{title}` / `state{data}` / `log{level,message}` | 界面、标题、状态、日志 |
| 框架→宿主 | `rpc{id, method, params}` | `files.stat/readText/readBytes/requestFileops`、`storage.get/set/delete/keys`、`permissions.request` |
| 宿主→框架 | `init{pluginId, hostVersion, adapterApiVersion, phase, manifest, mainUrl, theme}` / `open{item, adapter, state, permissions, fileToken, panelId}` | 启动 |
| 宿主→框架 | `rpc-result{id, ok, value \| error{code,message}}` / `action{action,payload}` / `theme{theme}` / `permission-denied{denial}` / `file-change{resourceId,change}` / `dispose` | 回应与事件 |

越界读取被主进程拒绝时，宿主除了让该次调用失败（`HostPermissionError`，code `out-of-scope`）外，还发 `permission-denied{reason:'out-of-scope'}` 并在面板顶部提示“已阻止一次越界读取”。

### 5.2 健壮性：进程隔离、看门狗、逐次调用超时（第五轮，T13）

**进程隔离（机制的前提）**：`kbplugin://<id>` 是独立的标准 scheme 站点，Chromium 的站点隔离把每个插件的 iframe 放进**单独的渲染进程**（out-of-process iframe），与主窗口渲染进程、与其他插件都不同；同一插件的多个面板共用一个进程。e2e 用 `WebFrameMain.osProcessId` 验证这一点（`pluginProcesses()` 的 `isolated` 字段，插件管理里显示“独立进程 · pid · 内存”）。所以插件死循环只占满它自己的进程，主窗口的事件循环不受影响，看门狗（运行在主窗口渲染进程）照常计时。没有另开 BrowserWindow / BrowserView：OOPIF 已经给出所需的隔离，且保持现有的 postMessage 协议与 UiNode 渲染不变。

| 情况 | 发现方式 | 处理 |
| --- | --- | --- |
| 同步死循环/长时间占满 CPU（打开时或运行中） | 心跳：就绪后宿主每 `HEARTBEAT_MS`=500 ms 发 `ping`，运行时回 `pong`（任何消息都算活着）；连续 `BUSY_MS`=3 s 没有回应 → 卡死 | 主进程 `killPluginFrames(pluginId)` 记下该插件子框架的 `osProcessId`；渲染进程随即卸载 iframe（框架干净分离，Chromium 随之结束这个不再承载任何框架的进程——实测 1 秒内 pid 消失）；主进程 250 ms 后兜底检查，进程仍存活、仍是本应用的 Tab 类型渲染进程、不是主窗口且不承载其他框架时才 `SIGKILL`（防止 pid 复用误杀）；面板显示 `adapter-error` 占位（原因 + 重试 + 从工作区移除）；同插件的其他面板一起变为占位（同一进程）；写审计 `watchdog` |
| 消息洪泛 | 1 秒窗口内超过 `FLOOD_MAX_PER_SEC`=400 条消息 | 同上（kind=flood） |
| `activate()` / `open()` / `mount()` 异步挂起 | 运行时 `withTimeout`：`LIFECYCLE_TIMEOUT_MS`=10 s → `open-error`；宿主兜底 12 s | `adapter-error` 占位（不杀进程，iframe 卸载即释放）；写审计 `timeout` |
| 插件 → 宿主的单次调用无回应 | 运行时每个 RPC `RPC_TIMEOUT_MS`=15 s → `HostPermissionError(code:'timeout')`；宿主侧同样 15 s 后回 `rpc-result{ok:false, code:'timeout'}` | 插件自行处理；写审计 `timeout`。需要用户操作的 `files.requestFileops` 与 `permissions.request` 不设超时 |
| 运行环境 15 s 未就绪（包损坏、被 CSP 拦截） | 就绪计时 | `adapter-error` 占位 |

- 误判防护：宿主自己的定时器迟到超过 1 秒（系统休眠、主窗口卡顿）时心跳计时重置，不归咎于插件；iframe 不在文档中时暂停计时。
- 主窗口渲染进程意外退出（不应发生）时主进程记录原因并重新载入窗口，布局从数据库恢复。
- **不足**：没有 CPU/内存配额（插件可以在不卡死事件循环的前提下吃满内存，直到进程被系统或 Chromium 杀掉；那时心跳停止，按卡死处理）；Windows 上 `process.kill` 等价于 `TerminateProcess`，未在 Windows 上验证；如果将来 Chromium 把插件 iframe 放回主进程（`isolated=false`），看门狗无法单独停止它——插件管理会显示“与主窗口同一进程”。

### 5.3 审计记录

主进程表 `plugin_audit(id, at, last_at, plugin_id, adapter_id, kind, code, detail, count)`（DB v5）。记录：

| kind | 何时 |
| --- | --- |
| `denied` | `files.*` 或 `kbfile://plugin` 请求被拒（`permission-denied` / `out-of-scope`），detail 为“操作 根名/相对路径：原因” |
| `grant` | 允许、拒绝、撤销某项权限 |
| `plan-submitted` / `plan-blocked` | 批量计划通过/未通过预检（列出每步“操作 根名/相对路径”） |
| `plan-rejected` / `plan-approved` / `plan-failed` | 用户拒绝 / 批准并执行（含操作记录编号）/ 批准后复查或执行失败 |
| `watchdog` / `timeout` | 看门狗终止 / 生命周期或调用超时（只有这两类允许渲染进程写入） |

不含绝对路径与文件内容。同一插件、同类、同内容 2 秒内重复的合并为一条（`count` 累加），每个插件最多保留 500 条，防止恶意插件刷爆数据库。插件管理中每个插件有“审计记录”折叠区（`pm-audit-<id>`，可“只看拒绝与异常”），每 2 秒刷新。卸载时“保留数据”保留审计，“删除数据”一并删除；卸载对话框显示条数。

### 6.1 files.* 与 kbfile 授权（H5）
每次调用都按顺序检查：插件已安装、启用、兼容 → 适配器是 file 适配器且声明了 `fs.read` → 授权为 granted 且 `declHash` 与当前声明一致 → `resourceId` 字符集合法 → 资源存在且是文件 → 资源所在根在授权的 `rootIds` 中、扩展名在声明的 `extensions` 中 → 经路径校验解析出绝对路径（只在主进程内使用）。`readText` 默认最多读 5 MB，硬上限 16 MB（返回 `truncated`）；`readBytes` 每次最多 4 MB。
`kbfile://plugin/<token>/<resourceId>`：令牌绑定“插件 + 适配器”，每次请求重新做上面的检查；伪造、已释放、属于别的插件的令牌一律 403。`kbfile://res|root` 在沙箱内被 CSP 拦截。

## 7. 占位（H6）

所有占位都是 `ui/Placeholder.tsx`，`data-testid="placeholder"`、`data-kind`、`data-source-kind`、`data-adapter-id`。判定顺序（SDK §5.1）：适配器解析（`adapter-missing/disabled/incompatible/error`）→ 阶段（`phase-unavailable`）→ 资源（`resource-missing`）→ 权限（`permission-denied`）→ 范围预检（文件所在根/扩展名不在授权内 → `permission-denied`）→ 运行（`open-error/activate-error` → `adapter-error`）。

| 动作 | 行为 |
| --- | --- |
| 安装插件… | 打开插件管理（开发者模式安装） |
| 启用插件 | 启用提供该适配器的插件 |
| 查看权限… | 打开插件管理并定位到该插件 |
| 用内置阅读器打开（仅本次） | 用最匹配的内置阅读器临时显示；**不改写**条目的 adapterId 与状态，可“恢复” |
| 重试 | 重新解析资源 / 重新启动沙箱 |
| 从工作区移除 | 确认后关闭面板并删除条目 |
| 回到首页（`domain-blocked`） | 条目 `ref` 改为适配器声明的 `web.homeUrl`、清空状态，随即打开网页面板（第六轮） |
| 用系统浏览器打开…（`domain-blocked`） | 确认框 → `webOpenExternal(url)`，与横幅同一规则：只允许 https、不含账号密码（D2，主进程再查）；不是 https 时按钮禁用并说明原因（第六轮） |
| 定位程序… | P3 才有意义，当前显示为禁用 |

`domain-blocked`（条目地址不在 net 域名内）与 `network-offline`（主框架加载失败，面板内显示，带“重试”）在第六轮可触发；`app-not-installed`、`app-verification-failed` 要到 P3。

## 8. 卸载（H7，D3）

卸载对话框（`uninstall-dialog`）：二选一“保留数据（重新安装后恢复）/删除数据”（默认保留）；列出插件存储（项数、字节）、授权记录条数、网站数据（插件没有 web 适配器时为“无”；有时读取 `persist:kbweb.<id>` 分区大小）；复选框“同时从工作区移除由它显示的 N 个条目（涉及 M 个工作区）”，默认不勾。
- 保留数据：删除插件文件，`plugins` 行标记 `uninstalled_at`，存储与授权保留；工作区条目保留，显示 `adapter-missing` 占位；重装后自动恢复到原状态。
- 删除数据：删除 `plugins` 行与 `plugin_kv`；有网页适配器时先销毁该插件的所有网页视图，再对其分区 `clearStorageData()`（Cookie、localStorage、IndexedDB、Service Worker、Cache Storage、文件系统）+ `clearCache()`。网站数据占用 = 分区 HTTP 缓存 + `userData/Partitions/<分区>` 目录大小。
- 移除条目：在所有工作区删除该插件适配器的条目，并从 dock 中剪掉对应面板（空分组一并去掉）；当前工作区随后从数据库重新载入。

### 8.1 导出、导入与备份中的插件数据（第五轮）

- **元数据库备份**（`WorkbenchService.backupTo`，SQLite 在线备份）：整库复制，因此**已经包含** `plugins`（启用状态、授权 `granted_json`、`uninstalled_at`）、`plugin_kv`（插件存储）与 `plugin_audit`（单测验证）。不包含插件包本体（`userData/plugins/<id>/`），恢复后需重新安装插件；数据会自动对上。备份目前只有服务层接口，UI 中没有“备份/恢复”入口（与第三轮相同）。
- **工作区导出 `.kblayout.json`**：只增加 `plugins: [{id, name, version, adapterIds}]`——条目用到的第三方插件清单；导入时返回 `missingPlugins`，提示“需要安装插件：…（相关面板暂为占位）”。**有意不包含插件存储与授权**：
  1. 插件存储是插件全局的（例如插件自己的设置），不属于某个工作区；把它放进工作区文件会在导入时覆盖另一台电脑上同一插件的数据，且多个工作区文件之间互相冲突。
  2. 授权绑定本机的根 ID 与声明指纹，并且必须由用户在本机批准——导入一个文件不能替用户授予读取文件夹或修改文件的权限（否则分享一个工作区文件就等于分享权限）。
  3. 每个面板的视图状态（例如 JSON 树的展开节点）本来就在条目里，随工作区导出，导入后装上插件、授权即恢复。

## 9. 批量计划（H8）

插件调用 `ctx.files.requestFileops(plan)`（只有声明了 `fileops.write` 的适配器才有这个方法）：
1. 渲染进程：确保 `fileops.write` 已授权（未询问则弹授权框；拒绝 → `{ok:false, reason:'permission-denied'}`）。
2. `planPreview(pluginId, adapterId, plan)`（主进程）：校验授权；步骤 1–100 个、类型 ∈ 声明的 `operations`（否则 `out-of-scope`）、每步资源都在该适配器的 `fs.read` 授权范围内、总内容 ≤5 MB；调用引擎 `preview` 得到每步说明与冲突；返回 `PlanPreviewDto{planId, pluginName, title, steps[{op, rootName, relPath, toRelPath?, summary, bytes?, conflicts[]}], engine, blocked}`，计划在主进程保留 10 分钟。
3. 渲染进程弹出计划对话框（`plan-dialog`）：逐步列出，冲突时“批准”不可用。
4. 批准 → `planExecute(planId)`：再次检查授权与范围，调用引擎 `execute(plan, 'plugin:<id>')`，返回 `{ok:true, opIds}`；拒绝/关闭 → `planDiscard(planId)` → `{ok:false, reason:'user-rejected'}`。

**引擎接口**（`src/main/service/plan.ts`，供 `@kb/plan` 接入）：
```ts
interface FileopsPlanEngine {
  readonly name: string;
  preview(plan: FileopsPlan): PlanStepCheck[];               // 无副作用：{step, preview: OpPreview|null, conflicts: string[]}
  execute(plan: FileopsPlan, actor: string):                  // 只在批准后调用；每步写 op_log(actor)，返回 opIds
    { ok: true; opIds: number[] } | { ok: false; reason: 'conflict'; detail: string; opIds: number[] };
}
```
引擎不做授权判断（由 `PluginHostService` 负责）。当前 `StubPlanEngine` 基于现有 fileops：顺序执行、**不是事务**（中途失败时已执行的步骤保留，可在操作记录中逐条撤销），`expectedHash` 不一致报冲突。`@kb/plan` 接入时替换 `PluginHostService` 构造函数里的引擎即可，IPC 与对话框不变。

## 10. 与 SDK 规范的差异 / 需要 SDK 侧跟进的变更

> **状态（第五轮）**：下列 1–6 已在 SDK 修订 2（`050df08`，规范 §15 第 2 条）中全部采纳，核心与 SDK 目前没有未决差异。保留原文作为记录。第五轮新增的健壮性参数（心跳 500 ms / 卡死 3 s / 生命周期 10 s / RPC 15 s / 洪泛 400 条每秒）与 `pong` 消息是核心实现细节，插件无需感知；如果 SDK 想在规范中写明“插件不得长时间占用事件循环、调用会超时（code `timeout`）”，可参考 §5.2。

1. **模板 README 需写明分发格式**：`main` 必须是单文件 ES 模块（核心按 `import('kbplugin://<id>/<main>')` 加载，不解析裸模块名）；推荐用核心的 `npm run plugin:build` 打包。
2. **卸载保留数据的记录方式**：核心用 `plugins.uninstalled_at` 标记，而不是删除行；SDK 文档若描述了不同的存储方式，请以“保留授权与存储、重装后恢复”为准对齐。
3. **CSP `img-src` 收窄**：规范写 `img-src kbfile:`，核心收窄为 `kbfile://plugin`（`kbfile://res|root` 不按插件授权，不能让沙箱访问）。规范 §4 写 `contentUrl()` 返回 `kbfile://res/<id>/<name>`，核心返回 `kbfile://plugin/<面板令牌>/<resourceId>`（令牌绑定插件 + 适配器，每次请求按当前授权检查）。请把规范改为“形式由宿主决定、插件不得自行拼接”。
4. **`ReaderMountTarget.element` 未提供**（`types.ts` 注释说自绘阅读器可改用它）：v1 只有 UiNode 渲染，iframe 不可见。需要自绘的阅读器（如 pdf.js）要等后续版本让 iframe 可见并处理尺寸/焦点/快捷键桥接。
5. **布局 schema 编号**：规范把“条目 + 面板只引用 itemId”的布局称为 schema 3；核心的 schema 3 已在第三轮用于“内联条目”，独立条目表的版本为 **schema 4**。
6. 必需的 `fileops.write` 会在打开时就询问；需要“首次修改时才问”的插件应声明 `optional: true`（示例 `e2e/fixtures/plugins/notes`）。建议规范写明这一点。

### 10.2 第七轮（SDK e72e619）
- `PluginAccessCode` 即 SDK 的 `HostErrorCode`（含 `timeout`），`PLUGIN_ACCESS_CODES` 在编译期与之核对；渲染进程宿主侧与沙箱运行时的超时错误都以 `code:'timeout'` 返回，未分类错误为 `'error'`。
- 真实 MDN 实测（B16b/B16c）：被拦截的只有 incoming.telemetry.mozilla.org；交互示例与其图片都来自 `*.mdnplay.dev`；兼容性数据来自 bcd.developer.mozilla.org；Array.map 与 img 两页没有请求 mdn.github.io（声明保留无害，供 SDK 参考）。

### 10.1 第六轮（H9）需要 SDK 侧确认或写进规范的点
1. **域内弹窗也拒绝**：`window.open`/`target=_blank` 一律不在应用内开新窗口（包括允许域名内）；域外弹窗按 D2 走横幅 + 确认 + 系统浏览器。规范 §12.2 只写了“弹窗限制在声明域名”，建议明确“宿主可以拒绝所有弹窗”。
2. **子资源检查发生在页面自身 CSP 之后**：页面 CSP 已经挡掉的请求不会到达 `onBeforeRequest`，所以“被拦截的外部资源”计数只统计 CSP 放行、但不在 `domains ∪ resourceDomains` 中的请求。真实 MDN 需要 `resourceDomains`（模板目前只声明 developer.mozilla.org，广告/统计脚本会被拦截，页面仍可正常阅读）。
3. **z-order**：原生 WebContentsView 无法与 DOM 混排，核心用“浮层相交即隐藏 + 显示最近一帧截图”（§11.3）。建议规范写明：宿主可以在浮层出现时临时隐藏网页面板，插件不应依赖网页一直可见。
4. **`openExternal` 的来源限制**：宿主只允许打开 https、无 userinfo、且是该面板最近被拦截（或条目 `ref` 本身）的地址；插件不能借 RPC 打开任意地址。建议写入 §12.2 / D2。
5. **`session.maxAgeDays` 的含义**：核心按“该插件 N 天未创建网页面板”清理分区（不是 Cookie 的绝对年龄）。
6. **`WebPanelHandle.currentUrl`** 是同步属性，核心用主进程事件缓存（导航完成后更新），刚调用 `navigate` 时可能仍是旧值。
7. **滚动恢复**：`setScroll` 到达目标后，页面晚加载内容仍会移动位置；建议模板在 `onLoadState('ready')` 之外，再在第一次稳定的 `onScroll` 前允许重试，或规范说明恢复是“尽力而为”。
8. 测试限制：e2e 中的分隔条拖动用 CDP 鼠标事件发给主窗口（指针在 DOM 分隔条上，不在原生视图上），没有用真实 OS 指针。

## 11. 网页面板（H9，第六轮）

SDK §6.3 / §12.2（`050df08`）。代码：主进程 `src/main/webPanels.ts`（`WebPanelManager`），共享判定 `src/shared/webPanel.ts`，渲染进程外框 `src/renderer/sandbox/WebSurface.tsx`（由 `SandboxPanel` 在 web 适配器时使用），插件侧 `WebMountTarget`/`WebPanelHandle` 在沙箱运行时 `src/plugin-runtime/runtime.ts`。

### 11.1 结构
- web 适配器与 file 适配器一样运行在沙箱 iframe 里（同一个运行时、同一套看门狗）；它拿到的挂载目标是 `{kind:'web', web: WebPanelHandle}`。`navigate/back/forward/reload/getScroll/setScroll/clearSessionData` 都是 RPC（`web.*`，白名单见 `sandboxProtocol.ts`），由面板转给主进程；插件**拿不到** viewId、webContents、执行脚本或改请求头的能力。
- 网页本身是主进程为每个面板创建的 `WebContentsView`（不是 `<webview>` 标签），加在主窗口 `contentView` 上。`webCreate(viewId, pluginId, adapterId)` 先调 `PluginHostService.webAccess`：插件已安装/启用/兼容、适配器 `sourceKinds=['web']` + `in-app-web` + 有 `web` 选项、必需的 `net` 权限已授予且 `declHash` 一致；域名、分区名、策略**全部取自 manifest**，渲染进程传来的不采信。面板卸载（关闭、切换工作区、看门狗停止、撤销、禁用、卸载）时销毁视图；主进程在撤销 net 权限、禁用、卸载插件、主窗口重新载入时也会主动销毁。
- 打开顺序（SDK §5.1 之后）：net 权限（未询问 → 授权框；拒绝 → `permission-denied` 占位）→ 条目地址 `checkNavigation(ref, domains)`（不通过 → `domain-blocked` 占位）→ 创建视图 → 启动沙箱 → 插件 `mount` 时 `navigate(恢复的 URL ?? ref)`。
- 新建网页条目：命令面板“打开网页面板：<适配器标题>…”（地址预填 `web.homeUrl`，只接受允许域名内的 https 地址）；条目 `ref` 用 `sanitizeUrlForState` 去掉 query 与账号。`window.__kb.openWeb(adapterId, url, mode)` 供 e2e 使用。

### 11.3 位置跟随与浮层（z-order）
- **跟随**：`WebSurface` 在面板里放一个“网页区域”占位元素，`requestAnimationFrame` 每帧读它的 `getBoundingClientRect()`（取整、裁到视口内），变化时经 `kb:web-bounds`（单向 `ipcRenderer.send`，主进程只接受主窗口发来的）发给主进程 `setBounds` + `setVisible(true)`。拖动分隔条、切换标签、最大化/还原、窗口缩放、侧栏拖动、横幅出现/消失都是同一条路径，所以视图永远与占位元素重合（e2e：拖动 10 步每步偏差 0 px）。
- **隐藏**：占位元素不在文档中、`checkVisibility()` 为假（非活动标签）、尺寸 < 2 px、主框架加载失败（面板内显示 `network-offline`）时发送 `null` → `setVisible(false)`。网页面板用 dockview 的 `renderer:'always'`：切换标签时 DOM 保留，网页视图只隐藏、不重建（e2e 验证同一 webContents）。切换工作区时面板卸载 → 视图销毁；切回时重建，URL 与滚动从条目状态恢复。
- **z-order**：原生视图总是画在主窗口 DOM 之上，CSS `z-index` 对它无效。处理办法是“相交即隐藏”：每帧检查工作台浮层（`OVERLAY_SELECTOR` = `.kb-dialog-backdrop`（所有对话框、插件管理、授权框、确认框）、`.kb-popover`（工作区菜单、外观菜单、命令面板、搜索结果）、`.states-sheet`、`[data-kb-overlay]`）是否与网页区域相交；拖放 dock 标签期间（`dragstart`→`dragend/drop`）也视为相交。相交时原生视图隐藏，占位里显示主进程缓存的最近一帧截图（滚动/加载稳定后 `capturePage()`，JPEG），因此页面看上去仍在、但菜单/对话框完整可见可点；浮层关闭后下一帧恢复。新增的工作台浮层只要带上这些类名之一或 `data-kb-overlay` 即可。e2e 用 X 屏幕截图（ffmpeg x11grab，包含原生视图）与 DOM 截图逐像素比较菜单区域与对话框下的网页区域，差值 0。
- 限制：坐标按主窗口缩放 100% 计算（工作台没有页面缩放功能）；浮层只隐藏**相交**的网页面板，不相交的照常显示。

### 11.4 状态与恢复
- 模板的状态是 `{url（去掉 query）, scrollY}`。滚动由主进程在隔离世界（world 1001，页面脚本不可见）中每 300 ms 读取一次，变化时发 `onScroll`；`setScroll` 用 `scrollTo({behavior:'instant'})`，页面内容还在增长时最多重试 3 秒。插件在 `onLoadState('ready')` 时恢复滚动。
- 条目 `ref` 在创建与保存时都经 `sanitizeUrlForState`（`src/shared/items.ts`）。重启后不再询问权限（授权已记录），视图按状态中的 URL 打开并恢复滚动。e2e 检查：恢复的 URL 与保存的一致（无 query，保留 `#hash`），宿主 `setScroll` 到达保存的 scrollY（±2 px）；夹具模式下还要求最终 scrollY 一致。真实 MDN 上恢复后页面会被晚加载的内容（广告位、图片）再推动（一次测得保存 2100 → 恢复到 2100 → 稳定后 2492），宿主不会“追着页面改滚动”，这是已知限制。
- 写库：网页面板会在主进程频繁写审计与 `web.lastUsed`，和索引 worker 并发写同一个 SQLite（WAL）。所有写事务改为 `BEGIN IMMEDIATE`（`.immediate()`），否则延迟事务“先读后写”会直接报 `database is locked`（busy_timeout 对这种情况无效；第六轮的网页 e2e 暴露了这个旧问题）。

### 11.5 离开域名（D2）
被拦截的顶层导航/弹窗在面板顶部显示横幅（地址、原因、允许的域名、次数）。地址是 https 且策略为 `open-external-with-confirm` 时提供“用系统浏览器打开…”：二次确认后调用 `webOpenExternal(url, {viewId})`；主进程只接受 https、无账号密码、且**是该面板最近被拦截的地址**（渲染进程不能借此打开任意地址），然后 `shell.openExternal` 并写审计 `web-external`。`domain-blocked` 占位的按钮用同一规则（`{pluginId, adapterId}`，地址即条目 `ref`）。http/file/自定义协议一律不提供该按钮，直接调用也被主进程拒绝。

### 11.6 会话数据与测试夹具
- 持久分区保留到用户清除、卸载时选择删除，或超过 `maxAgeDays` 未使用（每次创建视图记录 `web.lastUsed.<pluginId>`，启动时清理过期分区）；`clearOnClose` 在该插件最后一个面板关闭时清除；插件可用 `clearSessionData(kinds)` 清自己的分区。网页会话数据不进入工作区导出与元数据库备份（它在 Electron 分区目录，不在 SQLite 中）。
- **测试夹具（仅测试）**：环境变量 `KB_TEST_WEB_FIXTURE=<目录>` 存在时，主进程在插件分区上 `protocol.handle('https')`，把 `https://<主机>/<路径>` 映射到 `<目录>/<主机>/<路径>`（没有该主机目录 → 502）。域名检查不变（`onBeforeRequest` 先于协议处理执行，e2e 在夹具模式下验证注入的域外图片/子框架/脚本/fetch 都被它拦截）。正式运行不设置此变量。`e2e/fixtures/web/developer.mozilla.org/` 是模仿 MDN 的几页静态页面。`npm run e2e` 先在能连上时用真实 developer.mozilla.org 跑一遍，再用夹具模式跑一遍（`KB_E2E_WEB_MODE=fixture`）。

### 13.2 D6 收紧（替代“启动前复制整个资料根”）

- 默认只备份**要用外部程序打开的那个文件**；清单 `programs[].backup.include` 可追加最多 8 条相对目标文件夹的 glob（`*` `?` `**` `{stem}`），不能是绝对路径、`..`、整文件夹（`*`、`**`、`**/*`）。改 `backup` 会改变权限指纹并重新询问授权。
- 上限（SDK `DEFAULT_APP_BACKUP_LIMITS`）：每次 50 个文件 / 64 MB；保留 14 天；备份区 1 GB。
- **保留期统一为 14 天**（2026-10-04 产品决定）：启动前备份（`app-backups/`）和记入操作记录的外部改动备份（`blobs/` 里 `via: 'external-app'` 那条记录的写入前内容）都只保留 14 天。主进程启动后的延后任务里清理一次，之后每天检查一次（`WorkbenchService.purgeExternalBackups`）。到期时，在记录上标 `detail.backupExpired`，再删除不再被其他未过期记录引用的备份文件（备份库按内容寻址，编辑器保存的记录可能共用同一份内容，这种情况不删）。过期后，“操作记录”里那条显示「备份已过期，无法撤销」，撤销按钮变灰；面板上的“撤销外部修改”也会拒绝并给出同样的说明。
- 授权框与插件管理通过 SDK `describePermission` 显示可恢复说明的**全部条目**（2026-10-04 产品决定，SDK 修订 9）：“启动前备份：…”一行、每条“可恢复：…”各一行（目前 3 条）、“不可恢复：…”一行列出全部条目（原文见 SDK 规范 §6.4）。内容太长时对话框不超出窗口（`.kb-dialog` 最大高度为窗口高度减 140px），正文滚动，“拒绝/允许”按钮始终可见（截图 `verify/apps-permission.png`、`verify/apps-permission-scroll.png`）。

### 14.2 逐站授权（`net.mode = 'ask-per-site'`）
- 声明 `domains: []`；每个主机（精确主机名，不允许 IP / 端口 / 通配）第一次打开时由宿主询问“允许访问 <host>？”（http 地址同时标“不安全连接”）。允许 → `PermissionGrant.grantedHosts` 追加该主机（主进程 `grantSite` 计算 declHash）；拒绝 → 只在本次运行内记住（重启后再次打开会再问）。
- 插件级“撤销” → 整个适配器拒绝（`webAccess` 抛 permission-denied）；插件管理中逐个撤销已允许的网站（`site-revoke-<host>`），已打开的面板立即重新询问。“重新询问 → 允许”保留已允许的主机。
- 网页面板：顶层导航 / 重定向到未批准主机 → 主进程发 `site-prompt` 事件，界面询问，允许后继续导航，拒绝显示横幅“你拒绝了访问该网站”。子资源主机被拦截时，工具条列出被拦截主机，可逐个“允许…”（与页面主机共用同一份 grantedHosts）。授权变化时主进程 `refreshAccess` 推送 `access` 事件更新允许列表。

### 14.3 网络资料（`web_resources`）与稳定 ID
- 每条网址一个 UUID v4 `resourceId`；url 经 `sanitizeWebRef`：只允许 http/https，拒绝 IP / 端口 / localhost，去掉账号密码、query 与 fragment，上限 2048。同一 url 只有一条记录（再次打开复用 resourceId）。
- 表结构见 `src/main/webResources.ts`（`migrateWebResources(db)` 幂等建表，不占迁移号；待集成负责人追加到 MIGRATIONS）。
- 工作资料可以引用 web resourceId（`WorkspaceRef.sourceKind='web'`、`url`；rootId/relPath/ext 为空）。导出 `.kblayout.json` 带 `webResources`（url + 标题等），导入时按 url 重新匹配本机 resourceId（没有则新建）。网页条目本身是 `WorkspaceItem{sourceKind:'web', adapterId, ref:url}`。
- 侧栏“网络资料”面板：打开、收藏（排在前面）、加入本工作资料、复制网址、保存到本地、移除。命令：`web.openUrl`、`web.addToRefs`、`web.copyUrl`。

### 14.4 直链文件（PDF / 图片 / md / txt）与受控下载
- 网址扩展名在白名单内时用内置适配器 `web.file`（宿主内置，`in-app-web`）：主进程 `fetchForCache` 用 web.generic 的分区与授权逐跳请求（`net.request` + `redirect:'manual'`，每次重定向先检查目标主机，未批准 → 询问），超时 `KB_WEB_FETCH_TIMEOUT_MS`（默认 20 秒），上限 100 MB。
- 判型 `classifyWebContent`：Content-Type + 魔数 + 扩展名必须一致；`text/html` → 提示按网页打开；冲突 / 无法识别 → “无法识别类型，仍按网页打开 / 取消”，不静默按二进制解码。
- 缓存：`<数据目录>/web-cache/<resourceId>/<文件名>`（原子写入、只读权限）。通过 `WorkbenchService.externalResources` 钩子让现有阅读器把缓存当本地文件读（`getResource` / `resolveResourcePath` / kbfile）。网络资料只读：`textOpen` 返回不可编辑，`textSave` 等写入一律拒绝。
- 网络不可用 / 超时 / HTTP 错误 → 可重试占位，引用与 resourceId 保留；“重新下载”强制刷新缓存。

### 14.5 保存到本地
- 只写到已注册根内的**新文件**：默认 `网络资料/<文件名>`，同名自动加 “(2)”（`COPYFILE_EXCL`，不覆盖）；直链复制缓存文件，网页存 MHTML（`webContents.savePage`）。写入后记操作记录（`via: 'web-save'`）、触发索引；网络资料本身保留。渲染进程不写盘。

### 14.6 索引边界（网络正文索引后置）
- 不抓取、不索引网页正文。搜索只追加网络资料的标题 / 网址命中（`matchKind:'name'`）。已缓存的直链文件通过 `WebResourceStore.cachedFilesForIndex()` 暴露，交给索引组（E）按本地文件做正文索引（本轮未接）。
- 数据迁移包（docs/12）不含 `web-cache`（可重新下载）；`web_resources` 表随数据库迁移。
